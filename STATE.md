# STATE — Claude Companion: Single-Thread Orchestrator (PRJ-OR1T)

Last updated: 2026-09-07

## Active Decisions

### One always-open thread, workers report back tagged
**Date:** 2026-06-22
**Choice:** A persistent single chat thread (the "orchestrator") that never blocks. Heavy work is dispatched to spawned tmux Claude workers; each worker's turn-end reports back into the one thread, tagged by task-id.
**Why:** Inverts today's N-session-babysitting model. The orchestrator stays warm because it never does heavy compute itself. Validated via /office-hours + /brainstorm.
**Rejected:** raw-scrollback context (breaks "never computing" at scale); per-worker manual tab-tracking (the current pain).
**Revisit if:** thread volume needs multi-thread (schema already carries thread_id).

### Memory-proof gate cleared Phase 0
**Date:** 2026-06-22
**Choice:** Build the orchestrator on kb-v1 recall. Phase 0 suite (`~/.claude/evals/kb-memory-proof.ts`) proved accumulate + cross-session supersede + freshness, 5/5 baseline.
**Why:** The whole idea was gated on "is memory trustworthy." It is.

### Phase 1 scope: server-only, no client UI yet
**Date:** 2026-06-22
**Choice:** Ship the thread + dispatch plumbing + tagged worker-reply server-side, curl-verified. iOS/PWA UI is a separate, mobile-ux-gated phase.
**Why:** Keeps the build tight and defers the mobile-ux-auditor gate to the UI phase.
**Rejected:** building UI now (drags the mobile gate into plumbing work).

### Phase 7 autonomy shape: cap + FIFO + user-flipped auto
**Date:** 2026-09-05
**Choice:** WIP cap 3 live workers per host (`COMPANION_WIP_CAP` override), FIFO queue past it, per-channel `autoDispatch` toggle that only the user flips. Server reports trust (approved/rejected/streak, eligible at a 5-approval streak) and posts every auto-dispatch's reasoning in the thread. Cancel is the veto: it kills the worker and flips the channel back to propose-confirm.
**Why:** autonomy must grow with proof and stay one-tap reversible from the phone. The server suggesting is fine; the server deciding to go autonomous is not (CLAUDE.md agent-dispatch policy, Jevan "read its thoughts" rule).
**Rejected:** global auto toggle (trust is per project); server auto-enabling at the streak (removes the human from the ramp); per-cwd cap (host capacity is the real limit, not the project).
**Revisit if:** Mac + Zettlab need one shared queue (today each host caps independently).

## Change Plans

### Change Plan — phase10-per-session-activity (2026-09-10)
**Request:** PRJ-OR1T Phase 10 — make activity per-session. `server/lib/activity.ts:42` keeps ONE host-wide `let activity` (the pill: verb, tool, summary, elapsed, tokens) written by `recordToolStart`/`recordUserPrompt`, refreshed by `recordToolEnd`, cleared by `recordTurnEnd`/`forgetSession`, announced by `wiring/events.ts:98` and spread into `init` (`ws.ts:50`) and `/api/feed` (`routes/api.ts:315`). With several live sessions every hook overwrites the host's single pill, so the phone shows whichever session fired last and the PWA's `effectiveTarget` activity fallback follows it. Each session owns its own record; the host-level `activity` field becomes a derived rollup for shipped clients.
**Done when:**
- Two sessions working at once each keep their own pill; one session's tool call, turn-end or session-end never blanks the other's (server-verified + visible in the PWA picker).
- `lib/activity.ts` no longer holds `let activity` or `activityMatches()` — the map's `state:` column for it shows no host singleton.
- TestFlight build 4 improves on a **server-only** deploy (a finished session hands the pill back to the one still working instead of clearing it) and never regresses.

**Target shape & drift**
- **Reference = tmux** again (same leader as Phase 9; it is also what we inject into). Its model: `pane_current_command` is **per pane** — there is no global "what is running"; `window_activity` is a **per-window timestamp**; `session_activity` is documented as the session's last activity time, i.e. a **reduce over its windows**, computed on read. Mapping: their pane → our session's turn state (`verb`/`tool`/`summary`/`tokens`); `window_activity` → per-session `lastEventAt`; `session_activity` → the legacy host-wide `activity` field, derived as the max; status-line refresh interval → our 1.5 s poll, which refreshes every pane's data and redraws **once**, never once per pane.
- Reference for this intent: hook events mutate exactly one session's turn state; `lib/` owns state + listeners, `wiring/` turns listeners into frames, `routes/` are hosts; one record store per identity, with weak→strong key migration in one place; every rollup derived at read time; contracts additive for the shipped iOS build.
- Deviations today: the pill is a host singleton — a frame of reference recomputed from whichever session fired last · two `activityMatches(activity, s)` guards (`:168`, `:283`) plus a third, differently-shaped inline guard in `forgetSession` (`:293`) exist only to stop the singleton from being clobbered, i.e. the shape is already fighting itself · the 1.5 s poll interval is not `.unref()`-ed (`activity.ts:58`), unlike `sessions.ts:120` · `PathState` is only evicted by a session-end hook, so a SIGKILLed terminal leaks its state.
- This change moves toward: activity as a **property of the per-session record that already exists** (`transcript.ts`'s `states` map), rollup derived, plus the `.unref()` hygiene item. · Leaves for follow-up: an iOS build that reads `activities[]` and keys the pill per conversation (ios repo) · pruning dead `PathState`s themselves, not just their pills · a per-session pill for Codex sessions (`lib/codex-feed.ts` never sets activity today).

**State decisions**
- **The activity record lives on `PathState` in `lib/transcript.ts`** as `activity: Activity | null` + `lastEventAt: number`. `lib/activity.ts` stays the owner of the shape, the setter, the listeners, the rollup and the eviction policy; `transcript.ts` only holds the field (`import type { Activity }` — type-only, erased, so there is no runtime cycle). Persistence: **none**.
- **Why that map and not a new one:** `getState()` (`transcript.ts:50`) is already the first line of all five record functions, is already keyed `path:` > `tty:` > `sid:` > `cwd:`, and already **migrates a weak-keyed record onto the strong key in place** (`:64-80`). Riding it means the pill follows a session through identity upgrades for free — no parallel key space, no orphaning, and none of the collapse-carry special case Phase 9 needed.
- **Why NOT fields on `Session` (the Phase 9 shape):** lifecycle frequency. Waiting is a 2-field edge-triggered flag; activity is an 8-field record rewritten every 1.5 s by the heartbeat. On `Session` every beat would emit the `sessions` frame (the largest frame, full list, to every phone) **and** run `reconcileDispatch` (`wiring/orchestrator.ts:195-208` — an `await resolveWorkerTask` sqlite hit per session) at 1.5 s × N. It would also silently drop the pill for hook calls with no cwd, where `recordSession` returns null but activity works today. Different lifecycle → different home.
- **Eviction is the one thing the states map does not give us free, so it is explicit.** `forgetStates` matches on transcriptPath/tty/sessionId only, and a SIGKILLed terminal fires no session-end at all — with one pill that self-corrected on the next session's tool call; with N pills it would strand them. NEW `reconcileActivityLiveness(sessions)` in `lib/activity.ts`, called from the existing `onSessions` listener in `wiring/events.ts`: clear the pill of any activity whose `key` is not in the live session set **and** whose `lastEventAt` is older than 5 s. The grace window exists for exactly one race, now traced through all four hook types: `recordSession`'s collapse (`sessions.ts:259-281`) runs synchronously inside `recordSession`, *after* `sessions.set(key, next)`, so the caller's `session.key` is already post-collapse-fresh. What the 5 s protects is the **old** `PathState.activity.key` written by a prior hook, in the millisecond gap between the collapse's `emit()` and this handler's following `setActivity` refresh (PreToolUse has one `await judgeWithBranchContext` in that gap; the other three have none). Nothing else. It emits only when it actually cleared something, or it would broadcast at the 2 s dialog-poll rate.
- **Identity is issued, never inferred:** every record function takes a NEW `sessionKey` arg and every call site already holds the `Session` (`session?.key ?? ""`). Empty key = a hook with no cwd; the reconcile cannot judge those and skips them (they clear on turn-end / session-end exactly as today).
- **Rollup rule — order by `lastEventAt`, never by `lastBeatAt`.** `lastEventAt` is bumped only by real events (tool start, user prompt, tool end); the heartbeat bumps `lastBeatAt` only. Ordering on the beat would re-sort every 1.5 s and flip the shipped clients' pill between sessions — the derived frame of reference this phase exists to remove. `listActivities()` returns most-recent-event first; `getActivity()` is `listActivities()[0] ?? null`.
- **One frame per tick, not one per session.** The poll refreshes every live pill and then emits **once** (`emitActivity(key)`, `key: ""` for a heartbeat tick), so WS volume stays at today's rate whatever N is. All three anti-clobber guards go: each record function now writes only its own `PathState` (see the activity.ts Files row — two of them die with `activityMatches`, the third for a different reason).

**Target shape & drift**
- **Reference = tmux** (the leader for per-window attention state in a multiplexer, and the thing this repo already injects into). Its model: `monitor-activity` sets a **per-window** flag (`#{window_activity_flag}`, `#` in the status line); `#{session_activity_flag}` is documented as "1 if **any** window in session has activity" — the aggregate is **derived**, never stored; the flag clears when **that** window becomes current, never from another window's output; `alert-activity`/`visual-activity` are the notification hooks fired off the per-window flag. Mapping: their window → our `Session`; `window_activity_flag` → per-session waiting; `session_activity_flag` → the legacy host-wide `waitingForInput` in `init`/`/api/status`, derived; clear-on-visit → clear scoped to the session that received the input; `alert-activity` → our `waiting_input` frame + APNs. Record shape ("what, since when") from Kubernetes `status.conditions[]` (`type` + `lastTransitionTime`).
- Reference for this intent: hook events mutate exactly one session's state; `lib/` stores own state and emit listeners, `wiring/` turns listeners into frames, `routes/` are hosts, `state.ts` is transport plumbing only (`clients`, `broadcast`, `HOST_INFO`) that imports nothing from `server/`; every rollup is derived at read time; contracts additive for the shipped iOS build.
- Deviations today: waiting is domain state living in the transport module · it is a host singleton, i.e. **a frame of reference recomputed from whichever session fired last** — one session's turn-end shifts the phone's whole world · `lib/activity.ts` keeps the same shape (`let activity`, one pill for the host) · `wiring/orchestrator.ts:73` is a bare `setInterval` with no `.unref()` · `spawn-session.ts:338-340` exports a zero-caller `spawnClaudeSession()`.
- This change moves toward: waiting as a **property of the Session record**, host rollup derived; `state.ts` back to transport; the two hygiene items above (both one-file, no contract). · Leaves for follow-up: per-session `activity` (same singleton, bigger blast radius — file as Phase 10) · an iOS build that reads the new `init.waitingSessions[]` array (ios repo) · joining approvals/questions/dialogs into `waitingKind`.

**State decisions**
- **Per-session waiting lives on `Session` in `lib/sessions.ts`** as `waitingSince: number` (epoch ms, `0` = not waiting) + `waitingKind: string` (`"turn-end"` today). Mutated only by NEW `setSessionWaiting(key, kind)` / `clearSessionWaiting(key)`; announced on the existing `sessions` frame (the `taskId` precedent from Phase 8). Persistence: **none** (in-memory, dies with the record).
- **Why the record and not a new keyed map:** lifecycle. Waiting must be evicted by `prune()`, the identity-collapse branch and all four `removeSessionBy*` paths; on the record that is free, in a parallel map every one of the six is a leak that leaves a phantom waiting target alive forever.
- **Why not overload `agentStatus`/`waitingFor`:** two writers, one field. `wiring/dialogs.ts:33-35` polls `~/.claude/sessions/<pid>.json` every 2 s and calls `setSessionStatus`, which would clobber a hook-set value. Keep them separate and disjoint: `agentStatus` = Claude Code's own polled view (2 s lag), `waitingSince` = the hook's event-driven truth. Nothing joins them.
- **Rollup is derived, never stored:** NEW `waitingSummary()` in `lib/sessions.ts` returns `{ waitingForInput, waitingCwd, waitingKey, waitingSessions: [{key,cwd,kind,since}] }`, the three legacy scalars being the **most recent** waiting session (tmux's `session_activity_flag` rule). `ws.ts` init and `/api/status` spread it in place of `getWaiting()`.
- **Who clears (tmux clear-on-visit):** `POST /hooks/pre-tool-use` clears only its own `session.key` (it already holds `session` at hooks.ts:211); `session-end` + prune clear by removing the record; inject clears the explicitly named target only (next bullet).
- **Inject clears the caller's EXPLICIT target, never the delivery fallback.** NEW `clearWaitingForTarget(target: Session | null)` in `lib/sessions.ts`: with a target, clear it; with none, clear the single waiting session if exactly one waits, else clear **none** and log a refusal (Phase 8's refuse-on-ambiguity rule). **Both call sites must pass the target the request actually named.** `ws.ts:97-98` already holds exactly that. `routes/api.ts:179-181` does **not**: on a keyless request it reassigns `target` to `listSessions().find(s => !!s.tty)`, the most-recently-active session — and `lastSeenAt` is bumped by any session's tool call, so clearing that would blank a badge belonging to a session that never received the text. That is the derived frame of reference this whole change exists to remove. The builder captures the explicit target **before** line 179 and passes it to the clear; the fallback stays for `injectText` delivery only (the two are already decoupled — the clear at :208 does not feed the call at :211).
- `state.ts` **deletes** `getWaiting`/`setWaiting`/`clearWaiting` outright — no shim, no deprecation (house rule; the transitional-read exception is only for shipped-client frame fields, below).
