### Opus resolver: Opus 5.5 works every triage item before it reaches Jeremie; code decides what runs

**State decisions**
- Investigation records: Companion sqlite `body_investigations` (companion.db, created in `lib/body-investigate.ts` against the injected `Database`). Statuses `running | pending_host | forwarded | done | failed | dropped`. Open = running/pending_host/forwarded (≤ 1 per component). Writer: `wiring/body-investigate.ts` only. Persistence: sqlite; nothing in memory but the in-flight child processes.
- Trigger gate (pure, `gate()`): state ∈ dead|crash_loop|failing; no open record; cooldown 12 h after a `done` (or after 2 consecutive `failed`) for the SAME state — a different state, or an alert carrying a real transition (`from_state ≠ state`), breaks it; a single failure retries after 10 min. - Host routing: owner = `mac` for `mac:*`, `zettlab` for `zettlab:*`/`cloud:*`. Local host = `COMPANION_BODY_HOST` else darwin→mac, linux→zettlab. Own component → run here. The Mac never forwards (its sweep covers only `mac:*`; Mac dedupe makes Zettlab's forward + the Mac's own sweep idempotent).
- Reports: whoever owns #Body applies them (turn, proposal, Turso event, push). Zettlab applies locally. The Mac POSTs `{report}` to `COMPANION_BODY_PEER` (Zettlab) and falls back to its own #Body when that fails or no peer is set. Zettlab upserts the report onto its forwarded/pending record (or inserts it); a replayed report id is a no-op.
- Investigator: `claude -p` on the owning host, model `COMPANION_INVESTIGATE_MODEL` (default `sonnet`), 10 min timeout, prompt on stdin, cwd = `~/.claude-companion/investigate` (empty, stable — the CLI leaves one empty `~/.claude/projects/<cwd>/memory` per distinct cwd), env allowlisted (no Turso/Companion/broker tokens). Read-only by construction: `--setting-sources project,local` (user settings carry `defaultMode: auto`, `Bash(launchctl:*)` and hooks — never loaded), `--settings {"disableAllHooks":true}`, `--strict-mcp-config`, `--permission-mode dontAsk` (anything not allowlisted is denied, never prompted), `--tools Read,Grep,Glob,Bash`, `--add-dir /` (paths outside cwd are otherwise refused even for `ls`), `--allowedTools` = Read/Grep/Glob + the diagnostic Bash prefixes, `--disallowedTools` = Edit, Write, NotebookEdit + secret paths + mutating flags (`curl -X/-d/-o…`, `git --output`, `journalctl --vacuum…`), `--no-session-persistence`. Zettlab 2.1.284 not verifiable from here (tailnet SSH policy) — first Zettlab run is the check.
- Output: strict JSON `{rootCause, evidence[], confidence 0-1, severity low|med|high|critical, recommendedFix {summary, steps[], risk low|med|high, reversible} | null, retire, notes}`; fenced or prose-wrapped JSON is extracted; anything else → `failed` ("unparseable"). Every text field is passed through `redactSecrets` before it is stored or posted.
- Proposal: the existing `createProposal` in #Body. noteId = `COMPANION_BODY_NOTE_ID` (default `projects/2026-06-22-companion-orchestrator`, PRJ-OR1T), agent = `builder` when a git repo is known for the component, else `claude`; cwd = that repo / the unit's working dir, else `~/.claude`. - Push: only severity high/critical, or a second consecutive failed investigation. Same sender gate as alerts (`bodyPushEnabled`).

### Change Plan — orchestrator-one-queue (2026-10-03)
**Request:** "Make the Companion orchestrator the brain's face, merged with dispatch: one queue." Turso `tasks` becomes the only work queue. Orchestrator chat files, shows, unblocks, requeues and cancels Turso agent tasks per channel. #Body brings vitals, alerts and blocked-work triage. Touches ~/claude-companion, ~/.claude/tools (dispatch.sh, dispatch-run.ts, dispatch-reconcile.ts; pm-nightly.py audited, no change), the tls-dashboard-v2 schema, and the iOS app.
**Done when:**
- A proposal approved (or auto-filed) in a channel shows up as a Turso task (`agent:<slug>`, `queued`) in /today. No new `orchestrator_tasks` row runs headless.
- Each channel lists its project's dispatch tasks live: queued/running/blocked/pr/completed/failed/cancelled, with PR link and result ref. Blocked tasks can be answered and requeued from the phone. Cancel works for queued, blocked and failed tasks.
- The brain in #Body gets the body digest plus the blocked-queue digest. The new iOS build shows vitals and `body_alert` there.

**Target shape & drift**
- Leader reference: Linear Agents API (developers.linear.app/docs/agents) and GitHub Copilot coding agent ("assign issue → PR"). Mapping: Issue → `tasks` row · Issue.delegate → `assignee agent:<slug>` · AgentSession → one run (`dispatch_run_id`) · session `awaitingInput` + `elicitation` activity → `blocked` + `dispatch_blocker` · the human's reply to the elicitation, which resumes the session → **unblock** (answer appended to `description`, then requeue) · `response` activity → result note (`dispatch_result_ref`) · PR attachment → `dispatch_pr_url` · Project → `notes` (projects/) · agent activity log → `agent_activity`.
- Reference for this intent: (1) one durable queue as the system of record. Chat, /today, dashboard and Telegram are views that issue commands; no surface owns a private task table. (2) Every writer uses guarded compare-and-set transitions plus an append-only ledger row. (3) Runners claim work atomically: headless dispatch-run, or the Companion live-pane runner. The brain only proposes and files work. (4) Status flows from the record (poll); a push is only a nudge and never carries state. (5) Projects are the grouping key and a channel is a view onto one project. (6) Additive DTOs on one WS.
- Deviations today: two queues and two state vocabularies (sqlite `orchestrator_tasks` vs Turso). The PR URL and result ref live only in the note body, and dispatch-reconcile regex-parses them. There is no `cancelled` state. `dispatch.sh` UPDATE is unguarded (last writer wins). dispatch-run's prompt is `tasks.text` only, so there is no way to answer a block. Channels map to a project only by `cwd`. `orchestrator-chat.ts` holds db, turns, tasks, channels and trust (508 lines, 36 exports). `reapStalled` assumes every `running` row belongs to dispatch-run. iOS `Models.swift` (775) and `CompanionSocket.swift` (649) are over cap. STATE.md decision "Phase 7 autonomy… Revisit if: hosts need one shared queue" — this is that revisit.
- This change moves toward (1)–(6) and fixes all the dispatch-side deviations above. Left for follow-up: F1 brain-issued actions (requeue/unblock from a chat sentence) · F2 accept/mark-done from the phone · F3 split dispatch-run.ts (621) into runner + `dispatch-repos.ts` · F4 dispatch-reconcile reads the env token first (today it reads the dashboard .env only) · F5 /today shows `cancelled` and the Companion source · F6 split CompanionSocket.swift · F7 drop legacy local task history after 90 days read-only.

**State decisions**
- Work queue (status, assignee, blocker, run, PR, result): Turso `tasks`. Writers: dispatch-run.ts/dispatch.sh (claim, run outcome, stall), pm-nightly.py (NULL→queued, orphan close), dispatch-reconcile.ts (merged→done), and Companion `lib/dispatch-tasks.ts`. Companion's operations are file, cancel, requeue, unblock, claimLive, finishLive. Every UPDATE is guarded `AND dispatch_status IN (<expected>)`, and every write has an `agent_activity` row (`dispatch:<state>`, meta `{source:"companion",host,channel}`). The change is announced by the `orchestrator_task` frame, emitted by the `wiring/dispatch.ts` poller. Persistence: Turso.
- New Turso columns: `dispatch_result_ref`, `dispatch_pr_url` (TEXT, nullable). dispatch-run is the only writer. New state `cancelled` (sets `done=1`; requeue sets it back to `done=0`).
- Proposals stay in Companion sqlite `orchestrator_tasks` (`proposed|rejected|filed`) with a new column `dispatch_task_id`. Filing flips `proposed→filed` and stamps a pre-generated 32-hex Turso id in one sqlite UPDATE, then runs `INSERT OR IGNORE` into Turso with that id. Retries are therefore idempotent. Rejected drafts never reach Turso, and pm-nightly cannot queue a draft. `listTasks` hides `filed`.
- Tmux worker runner is **kept as opt-in "live" mode** (Phase 4), not retired. It is the only path with a watchable pane and mid-task phone approvals (29/33 ok). Its record is a Turso row claimed at filing: `running`, `dispatch_owner='companion:<host>'`. dispatch-run only picks `queued` rows and its reaper skips `companion:%`. The local row keeps the tmux identity. The WIP cap of 3 applies to live mode only. Default mode is headless.
- Legacy history (pre-Phase-2 local tasks) stays read-only in sqlite and is listed with `source:"local"`. There is no migration into Turso: those rows have no note_id, and Turso `note_id` is NOT NULL.
- Channel ↔ project: `orchestrator_channels.note_id` plus a cached `note_title` and `note_ref`. There is at most one non-archived channel per note_id. Set by create with `noteId` or by `POST channels/<id>/link`; announced by `orchestrator_channel`. A channel's tasks are those whose `note_id` matches. #General shows agent tasks of unlinked notes plus everything filed from General. #Body shows blocked tasks across all notes.
- Status flow: the Companion polls Turso every 20 s. The poll query covers agent tasks updated since the cursor, plus open ones, over a 7-day window. `/hooks/dispatch-event` (stateless, rate-limited to one call per 2 s) triggers an immediate poll and is called by dispatch.sh after each transition. The diff is keyed on the value `(dispatch_status, updated_at, done, pr_url)`, not on counts. The announce cursor is persisted in sqlite table `dispatch_seen(task_id PK, status, updated_at)`, owned by `lib/dispatch-mirror.ts`, so a restart does not re-announce. A blocked or PR transition appends one orchestrator turn in the owning channel and fires a gated APNs push.
- Auth: Companion writes with the same `TURSO_AUTH_TOKEN` it already reads (agent env, never logged). Writes go only through named, guarded functions in `lib/dispatch-tasks.ts`; there is no generic SQL route. The phone never sees the token. Every new `/api/orchestrator/*` route stays behind the bearer gate. On HTTP 401 `turso.ts` clears the cached token and re-reads it once (rotation is pending per memory).

**Target shape & drift**
- Reference (Slack Web API file object, from its public reference): `file.id` maps to `mediaId`. `thumb_1024` + `thumb_1024_w/h` maps to our single 1024px JPEG + `width/height`. `url_private` (Bearer auth required) maps to `GET /api/media/:id`. The message carries a file *reference*, never bytes.
- Target: content-addressed media store in one leaf lib that does fs + encode only. Feed events carry references. Feed lifecycle (append/evict) is the only thing that frees resources. Routes stay thin. Clients switch on `kind` with a default.
- Target: transcript reader is incremental by byte offset, as `codex-feed.ts` already is with `offsets: Map`.
- Deviations today:
  - `readTranscriptDelta` does `readFileSync` + `JSON.parse` of the WHOLE transcript every 1.5 s tick. Screenshot sessions carry MBs of base64 per file.
  - The feed cap trim in `appendFeedEvent` is silent: no evict signal, so nothing can free resources tied to an event.
  - `FeedEvent` is hand-copied in three places: server `lib/feed.ts`, PWA `hooks/use-companion.ts:43-64`, iOS `WSFrame.swift:308`. No contract test.
  - `sharp` sits in devDependencies, unused by server code.
- Moves toward: a content-addressed store in a leaf lib (`lib/media.ts`), an explicit evict signal in `feed.ts`, and reference-not-bytes on the wire.

**State decisions**
- **Media files** live in `lib/media.ts`. The dir is `COMPANION_MEDIA_DIR ?? ~/.claude-companion/media`, which lets tests use a temp dir, same pattern as `COMPANION_DB_PATH`.
  - Mutated only by `storeImageBase64()`, `storeImageFile()`, `expireMedia()` and `enforceMediaCap()` (both via `sweepMedia()`). Persistence is plain files `<id>.jpg`.
  - `mediaId` = first 32 hex of sha256 of the source bytes. The same image read twice gives one file.
  - If `<id>.jpg` already exists, skip the encode, read dims via `sharp(path).metadata()` (header only), and `utimes` the file so the byte cap sees it as fresh.
- **Encode queue** is module-level in `lib/media.ts`: at most 2 concurrent sharp jobs, plus `sharp.concurrency(1)`. A burst of 50 screenshots must not starve the hook path.
- **Byte total** (`let mediaBytes`) is in `lib/media.ts`. It is seeded by one dir scan on first use and updated per write/unlink. When above 200 MB (`COMPANION_MEDIA_MAX_BYTES`), unlink oldest-by-mtime until under. There is no announcement: a phone fetching a pruned id gets 404 and shows a placeholder.
- **Seen images** use a new `PathState.seenImages: Set<string>` in `lib/transcript.ts`. Its keys are `tu:<tool_use_id>:<blockIdx>` and `md:<realpath>:<mtimeMs>`. The set is marked BEFORE the async encode, so the next 1.5 s tick never double-queues. A silent read marks the set without encoding.
- **Image events** use a stable id `img:<seen-key>`, so the feed id-dedupe makes re-reads idempotent and iOS can dedupe. `ts` is captured at detection, not after the encode, so the event sorts by when the tool returned.
  - Image events are NOT counted in `readTranscriptDelta`'s return value and do NOT set `streamedThisTurn`. `recordTurnEnd`'s retry and wrap-up policy (`activity.ts:332-358`) stay text-only.
- **Evict signal**: `feed.ts` gains `onFeedEvict(fn(evicted: FeedEvent[]))`. It fires on the cap trim and inside `pruneFeedForSession`. `feed_pruned` stays byte-identical: same ids, still session-prune only.
- **Media lifetime** is decoupled from the feed (2026-09-23). Files are never freed on feed eviction or session prune, because the phone's cached conversation outlives the 200-event feed and files are content-addressed and shared across sessions. `sweepMedia()` = age cap (`COMPANION_MEDIA_MAX_AGE` seconds, default 7 d, by mtime) + byte cap. It runs on every write, and `wiring/media.ts` also runs it at import and on a 1 h unref'd timer.

**Risks**
- **Full-file reparse per tick** scales with base64 volume. The encode is skipped via seen-set and file-exists, but the parse cost stays. The mitigation is follow-up 1; measure tick time on a 50-screenshot transcript in Verify.
- **Restart re-emission**: a restarted server re-reads history like it does for text today. The file-exists shortcut plus the 2-slot queue bound the cost to header reads.
- **Feed crowding**: computer-use sessions emit dozens of screenshots and the 200 cap evicts text sooner. Accept for now. If Jeremie's pass shows it, add a per-session image sub-cap as a follow-up.
- **iOS local cache**: a file freed by eviction or the byte cap can 404 while an old conversation still shows the row. The iOS half must cache bytes (URLCache honours `immutable`) and render a placeholder on 404.
- **Token in URL**: `?token=` works for `<img src>` but lands in logs. iOS must send the `Authorization` header.

Mapping: their condition `type` → our `WaitingKind`; one controller per type → one writer per reason (Stop hook owns `turn-end`, `lib/pty-manager` owns `approval`, `lib/questions` owns `question`, the dialog watcher owns `dialog`); `lastTransitionTime` → per-reason `since`; the READY column → `waitingKind`/`waitingSince` on the wire.
- Reference for this intent: hook events mutate exactly one session's state; `lib/` owns state + listeners, `wiring/` turns listeners into frames, `routes/` are thin hosts; every rollup derived; contracts additive for the shipped iOS build.
- Deviations today: `waitingKind` is a **single-writer scalar with one value** — any second writer would clobber the first, which is why Phases 9/10 kept the four signals disjoint · the phone must join four channels itself to answer "does this session need me" · four call sites hand-build the `waiting_input` frame, so a `waiting:false` from one of them can contradict a reason another still holds · `sessions.ts` (570/600) carries two things that are not the registry: `metaFromHeaders` (header parsing, sibling of `agentFromHeaders`) and the `ps` shell-outs.
- This change moves toward: waiting as a **reason list on the record with a derived projection**, one writer per reason, one module that owns the frame; plus the two `sessions.ts` extractions (which are also the cap relief this change needs). · Leaves for follow-up: an iOS build that reads `waitingKind`/`waitingRef` and deep-links the row to its approval/question/dialog (ios repo) · `codex exec` sessions register via hooks but are excluded from ps-discovery (`discover.ts:63`) — a pre-existing split identity, not this phase · a `dialog` reason for Codex panes (below).

**State decisions**
- **The reason list lives on `Session` in `lib/sessions.ts`** as `waitingReasons: WaitingReason[]` (`{kind, since, ref}`), beside the existing `waitingSince`/`waitingKind` and a NEW `waitingRef`. Same lifecycle argument as Phase 9: prune, the identity collapse and all four `removeSessionBy*` paths evict it for free; a parallel map would leak a phantom in six places. Persistence: **none**.
- **The scalars stay stored, as a projection recomputed on every mutation** — not read-time getters. `listSessions()` spreads raw records into four contracts (`sessions`, `init`, `/api/status`, `/api/feed`); a non-enumerable getter would silently vanish from all four. The list rides those frames too, on purpose: it is the conditions array the next iOS build reads.
- **Precedence is a pure function in NEW `lib/waiting.ts`** (DI seam, own unit test, zero imports): `resolveWaiting(reasons)` picks by `["dialog","approval","question","turn-end"]`, and **within one kind picks the OLDEST `since`** — the one blocking longest and the one whose 290 s expiry fires first. `approval` outranks `question` because an approval that expires resolves **"allow"** (`pty-manager.ts:56`) while a question that expires denies: the wrong-way-on-timeout one is the urgent one. `dialog` outranks everything because it is modal in the terminal — nothing else can be driven while it is up. **The order is load-bearing, not decorative:** nothing enforces mutual exclusion, since `dialog-watch.ts:62` guards only `hasPendingQuestion`, never pending approvals, so a dialog and an approval can sit on one session whenever Claude Code's status file races.
- **Re-asserting the same `(kind, ref)` does NOT reset `since`.** The badge's age is a property of when the block started, not of when we last noticed it. A new `ref` on the same kind is a new reason with a fresh stamp.
- **Reasons are keyed by `(kind, ref)`, so clearing is exact.** Two approvals on one session: `unmarkWaiting(key,"approval",id)` drops only that one and the projection falls back to the sibling. `ref` = the approval/question UUID, the dialog's session key; `""` for turn-end.
- **NEW `wiring/waiting.ts` owns the `waiting_input` frame; nothing else builds it.** `markWaiting(key,kind,ref?)` / `unmarkWaiting(key,kind,ref?)` mutate **and** announce, so a call site cannot mutate without announcing. The frame always carries the **derived** state after the mutation — a clear that leaves another reason broadcasts `waiting: true` with the surviving kind. That single rule is the whole point of the module; four hand-built frames could not honour it. It never pushes: APNs stays owned by the Stop path and by `wiring/events.ts`'s existing approval/question pushes.
- **Identity is issued, never inferred:** `ApprovalRequest` and `QuestionRequest` gain `sessionKey`, set by the route that already holds the `Session` (the Phase 10 `recordToolStart` precedent). `wiring/events.ts` — not the routes — joins the lifecycle to the waiting state, because that is what `wiring/` is for and because the **expiry** timers live inside the libs where a route could never clear the flag.
- **Collapse escape hatch, and it has two triggers, not one.** The collapse (`sessions.ts:259-280`) is one-directional (weak `sid:`/`cwd:` → strong `tty:`), and a request captures `sessionKey` once at creation (`hooks.ts:172,267,411`), so a later collapse leaves that key stale and the direct lookup misses. **The same staleness hits dialogs**, which the brief did not anticipate: `dialog-watch.ts:81`'s tick-driven liveness sweep fires `onDialogClosed(oldKey)` for a key already deleted. `clearSessionWaitingByRef(kind, ref)` is the fallback — an exact match over a handful of records, not a heuristic. It converges for dialogs because the carried reason keeps `ref = oldKey` verbatim; the cost is a brief window with two `dialog` reasons where `waitingRef` names a dead key. No `waiting:false` flicker, and the stale one is scanned out by that very close.
- **The dialog LIFECYCLE feeds `waitingKind`; the 2 s status poll does NOT** (revisiting Phase 9's two-writers call). `onDialog`/`onDialogClosed` are edge-triggered and deduped by signature, so they behave exactly like the approval/question lifecycles, and the reason list means the dialog writer can only ever touch its own slot. `agentStatus`/`waitingFor` stay disjoint: they are level-triggered, carry no `ref`, are `"waiting"` for turn-end too (double counting), and iOS build 4 already renders them as `CompanionSession.statusBadge` — changing their meaning is a shipped-client break. **Boundary rule this fixes in place: `waitingKind` only ever names a reason the phone has a detail channel for.** Claude Code can report `waitingFor: "dialog open"` while `parseDialog` returns null; the phone has nothing to tap then, so no `dialog` reason is set.
- **On the client, only `turn-end` feeds a rollup that speaks for the whole app.** `waitingByKey` keeps every kind (per-row dots, `targetWaiting` for the session you are on), but `newestWaiting` (`use-companion.ts:438-445`) filters to `turn-end`/`""` — and it is read by three things at once: `waitingForInput` → `status-bar.tsx:25`'s "Done", the `effectiveTarget` auto-follow (`:448-467`), and the alert gate. One predicate, `ANSWERS_TURN(kind)`, defined once at module scope in `use-companion.ts` so the three cannot drift apart. Without the filter, a question or dialog on a background session flips the header to "Done" (the PWA has no pending list for either — no `case "question"` exists in `client/src`) and, because a new `(kind,ref)` gets a fresh `since`, silently outranks an older turn-end and **switches which conversation the PWA sends to**. That is a derived frame of reference recomputed from whichever session most recently gained a reason — the exact shape Phases 9 and 10 removed from the server, and it must not reappear on the client.
- **An inject answers turn-end only.** `clearWaitingForTarget(target, "turn-end")`, and its "exactly one waiter" ambiguity check counts only sessions holding a **turn-end** reason. Text typed into a terminal does not answer a pending approval or close a dialog; those badges stay lit.

**State decisions**
- **The activity record lives on `PathState` in `lib/transcript.ts`** as `activity: Activity | null` + `lastEventAt: number`. `lib/activity.ts` stays the owner of the shape, the setter, the listeners, the rollup and the eviction policy; `transcript.ts` only holds the field (`import type { Activity }` — type-only, erased, so there is no runtime cycle). Persistence: **none**.
- **Why that map and not a new one:** `getState()` (`transcript.ts:50`) is already the first line of all five record functions, is already keyed `path:` > `tty:` > `sid:` > `cwd:`, and already **migrates a weak-keyed record onto the strong key in place** (`:64-80`). Riding it means the pill follows a session through identity upgrades for free — no parallel key space, no orphaning, and none of the collapse-carry special case Phase 9 needed.
- **Why NOT fields on `Session` (the Phase 9 shape):** lifecycle frequency. Waiting is a 2-field edge-triggered flag; activity is an 8-field record rewritten every 1.5 s by the heartbeat. On `Session` every beat would emit the `sessions` frame (the largest frame, full list, to every phone) **and** run `reconcileDispatch` (`wiring/orchestrator.ts:195-208` — an `await resolveWorkerTask` sqlite hit per session) at 1.5 s × N. It would also silently drop the pill for hook calls with no cwd, where `recordSession` returns null but activity works today. Different lifecycle → different home.
- **Eviction is the one thing the states map does not give us free, so it is explicit.** `forgetStates` matches on transcriptPath/tty/sessionId only, and a SIGKILLed terminal fires no session-end at all — with one pill that self-corrected on the next session's tool call; with N pills it would strand them. NEW `reconcileActivityLiveness(sessions)` in `lib/activity.ts`, called from the existing `onSessions` listener in `wiring/events.ts`: clear the pill of any activity whose `key` is not in the live session set **and** whose `lastEventAt` is older than 5 s. The grace window exists for exactly one race, now traced through all four hook types: `recordSession`'s collapse (`sessions.ts:259-281`) runs synchronously inside `recordSession`, *after* `sessions.set(key, next)`, so the caller's `session.key` is already post-collapse-fresh. What the 5 s protects is the **old** `PathState.activity.key` written by a prior hook, in the millisecond gap between the collapse's `emit()` and this handler's following `setActivity` refresh (PreToolUse has one `await judgeWithBranchContext` in that gap; the other three have none). Nothing else. It emits only when it actually cleared something, or it would broadcast at the 2 s dialog-poll rate.
- **Identity is issued, never inferred:** every record function takes a NEW `sessionKey` arg and every call site already holds the `Session` (`session?.key ?? ""`). Empty key = a hook with no cwd; the reconcile cannot judge those and skips them (they clear on turn-end / session-end exactly as today).
- **Rollup rule — order by `lastEventAt`, never by `lastBeatAt`.** `lastEventAt` is bumped only by real events (tool start, user prompt, tool end); the heartbeat bumps `lastBeatAt` only. Ordering on the beat would re-sort every 1.5 s and flip the shipped clients' pill between sessions — the derived frame of reference this phase exists to remove. `listActivities()` returns most-recent-event first; `getActivity()` is `listActivities()[0] ?? null`.
- **One frame per tick, not one per session.** The poll refreshes every live pill and then emits **once** (`emitActivity(key)`, `key: ""` for a heartbeat tick), so WS volume stays at today's rate whatever N is. All three anti-clobber guards go: each record function now writes only its own `PathState` (see the activity.ts Files row — two of them die with `activityMatches`, the third for a different reason).

**Target shape & drift**
- **Reference = tmux** (the leader for per-window attention state in a multiplexer, and the thing this repo already injects into). Its model: `monitor-activity` sets a **per-window** flag (`#{window_activity_flag}`, `#` in the status line); `#{session_activity_flag}` is documented as "1 if **any** window in session has activity" — the aggregate is **derived**, never stored; the flag clears when **that** window becomes current, never from another window's output; `alert-activity`/`visual-activity` are the notification hooks fired off the per-window flag. Mapping: their window → our `Session`; `window_activity_flag` → per-session waiting; `session_activity_flag` → the legacy host-wide `waitingForInput` in `init`/`/api/status`, derived; clear-on-visit → clear scoped to the session that received the input; `alert-activity` → our `waiting_input` frame + APNs. Record shape ("what, since when") from Kubernetes `status.conditions[]` (`type` + `lastTransitionTime`).
- Reference for this intent: hook events mutate exactly one session's state; `lib/` stores own state and emit listeners, `wiring/` turns listeners into frames, `routes/` are hosts, `state.ts` is transport plumbing only (`clients`, `broadcast`, `HOST_INFO`) that imports nothing from `server/`; every rollup is derived at read time; contracts additive for the shipped iOS build.
- Deviations today: waiting is domain state living in the transport module · it is a host singleton, i.e. **a frame of reference recomputed from whichever session fired last** — one session's turn-end shifts the phone's whole world · `lib/activity.ts` keeps the same shape (`let activity`, one pill for the host) · `wiring/orchestrator.ts:73` is a bare `setInterval` with no `.unref()` · `spawn-session.ts:338-340` exports a zero-caller `spawnClaudeSession()`.
- This change moves toward: waiting as a **property of the Session record**, host rollup derived; `state.ts` back to transport; the two hygiene items above (both one-file, no contract). · Leaves for follow-up: per-session `activity` (same singleton, bigger blast radius — file as Phase 10) · an iOS build that reads the new `init.waitingSessions[]` array (ios repo) · joining approvals/questions/dialogs into `waitingKind`.

**State decisions**
- **Per-session waiting lives on `Session` in `lib/sessions.ts`** as `waitingSince: number` (epoch ms, `0` = not waiting) + `waitingKind: string` (`"turn-end"` today). Mutated only by NEW `setSessionWaiting(key, kind)` / `clearSessionWaiting(key)`; announced on the existing `sessions` frame (the `taskId` precedent from Phase 8). Persistence: **none** (in-memory, dies with the record).
- **Why the record and not a new keyed map:** lifecycle. Waiting must be evicted by `prune()`, the identity-collapse branch and all four `removeSessionBy*` paths; on the record that is free, in a parallel map every one of the six is a leak that leaves a phantom waiting target alive forever.
- **Why not overload `agentStatus`/`waitingFor`:** two writers, one field. `wiring/dialogs.ts:33-35` polls `~/.claude/sessions/<pid>.json` every 2 s and calls `setSessionStatus`, which would clobber a hook-set value. Keep them separate and disjoint: `agentStatus` = Claude Code's own polled view (2 s lag), `waitingSince` = the hook's event-driven truth. Nothing joins them.
- **Rollup is derived, never stored:** NEW `waitingSummary()` in `lib/sessions.ts` returns `{ waitingForInput, waitingCwd, waitingKey, waitingSessions: [{key,cwd,kind,since}] }`, the three legacy scalars being the **most recent** waiting session (tmux's `session_activity_flag` rule). `ws.ts` init and `/api/status` spread it in place of `getWaiting()`.
- **Who clears (tmux clear-on-visit):** `POST /hooks/pre-tool-use` clears only its own `session.key` (it already holds `session` at hooks.ts:211); `session-end` + prune clear by removing the record; inject clears the explicitly named target only (next bullet).
- **Inject clears the caller's EXPLICIT target, never the delivery fallback.** NEW `clearWaitingForTarget(target: Session | null)` in `lib/sessions.ts`: with a target, clear it; with none, clear the single waiting session if exactly one waits, else clear **none** and log a refusal (Phase 8's refuse-on-ambiguity rule). **Both call sites must pass the target the request actually named.** `ws.ts:97-98` already holds exactly that. `routes/api.ts:179-181` does **not**: on a keyless request it reassigns `target` to `listSessions().find(s => !!s.tty)`, the most-recently-active session — and `lastSeenAt` is bumped by any session's tool call, so clearing that would blank a badge belonging to a session that never received the text. That is the derived frame of reference this whole change exists to remove. The builder captures the explicit target **before** line 179 and passes it to the clear; the fallback stays for `injectText` delivery only (the two are already decoupled — the clear at :208 does not feed the call at :211).
- `state.ts` **deletes** `getWaiting`/`setWaiting`/`clearWaiting` outright — no shim, no deprecation (house rule; the transitional-read exception is only for shipped-client frame fields, below).

**Target shape & drift**
- Reference = Temporal's dispatch API (the leader for "which worker produced this callback"): `RespondActivityTaskCompleted(taskToken)` — the server issues an opaque token at dispatch and the worker echoes it on every callback; the task queue is routing only and never correlates a completion. **Fan-in paths to guard**

## Learnings

- **First `/change` run (2026-09-07):** the split shipped as 10 commits, `bun test` 50/50 + server tsc + a fixed route/WS/stderr smoke diffed against the pre-split baseline after every one. Both cross-module contract checks that the plan named paid off: the mechanical route extractor moved a section's *neighbours* along with it when an earlier extraction had removed the marker between them, so three chain calls ended up nested inside other route modules — every behavioural check stayed green (identical responses) and only the **import-boundary guard** ("no module imports routes or the host") exposed it. That is the boundary lint's job; wire it into CI (PRJ-LGDV Phase 4).
- Layout after the split: `state.ts` (clients, broadcast, host, waiting flag) · `lib/hook-common.ts` + `lib/tmux-pane.ts` (shared helpers) · `wiring/{orchestrator,dialogs,events}.ts` (singletons + listeners, side effects at import) · `routes/{hooks,api,orchestrator,dialogs}.ts` (each returns null for other paths) · `ws.ts` · host = auth gate, health, upgrade, route chain, static. Add a route to the matching `routes/` file, never to the host; new always-on state goes in `wiring/`.
- **Dialog mirror (PR #9, 2026-09-05):** a session parked on /model, /mcp, trust or MCP-enable looks dead from the phone — hooks don't fire while a dialog is up. `~/.claude/sessions/<pid>.json` says `status: waiting, waitingFor: "dialog open"`; that gates a 2s tmux capture, `dialogs.ts` parses the Ink dialog (cursor row + hint footer; numbered pickers and plain lists), and the phone gets `dialog` / `dialog_closed` frames plus `/api/dialog/key` and `/api/dialog/pick`. Row picks use Up/Down deltas: digits only work in the question picker, /model ignores them. Fixtures came from real captures — recapture if Claude Code restyles its pickers.
- **`~/.claude/sessions/<pid>.json` is the exact pid → session map** (Claude Code ≥ 2.1, found 2026-09-05): sessionId, cwd, startedAt, tmux pane, Claude's own derived name, status. Discovery now reads it instead of guessing the newest transcript in the cwd — the guess gave every $HOME peer the same id (and, once titles existed, the same name). Guessed ids are marked unconfirmed and never name a chat.
- **Chat titles = first real prompt**, persisted by session id, recovered from the transcript (any project dir) on restart; injected XML is stripped first. Picker sorts on creation time (process start), not last activity — activity-sorted menus reshuffle on every hook fire.
- **AskUserQuestion picker grammar (Claude Code 2.1.x, mapped live 2026-09-05):** tab bar `← ☐ Q1 ☐ Q2 ✔ Submit →`; digit N picks row N (single-select auto-advances, multi-select toggles); row `options+1` is "Type something" (free text, Enter confirms); Tab reaches "Review your answers", Enter submits; transcript then prints "User answered Claude's questions". Down/Space/Enter no longer apply. Drive it from the pane (`server/lib/question-driver.ts`), never from a timer.
- **Claude Code fires PreToolUse AND PermissionRequest for one AskUserQuestion** when both hooks match `*` (Linux host). Anything a hook does per question must be idempotent across the pair — `questions.ts` keeps a 180s answered-key record. Mac's PreToolUse matches only `Bash`, so only PermissionRequest fires there; both shapes verified. Companion's stderr goes to `~/.claude-companion/companion.log` on the Linux host too, not the journal.
- **Bun test shares the module cache across files** (2026-09-05): a second test file that sets `COMPANION_DB_PATH` and imports `orchestrator-chat` either gets ignored or steals the sqlite binding from the legacy-seed fixture, depending on run order. Rule: one test file per sqlite-bound module; DI'd modules (worker-tail, queue policy) can test anywhere.
- **Phase 11 shipped (2026-09-10, PR #23):** waiting is a reason list on `Session` (`waitingReasons: {kind,since,ref}[]`, Kubernetes `status.conditions[]` shape), one writer per reason (Stop → turn-end, pty-manager → approval, questions → question, dialog watcher → dialog), projected to `waitingKind`/`waitingSince`/`waitingRef` on every mutation (STORED, never getters — `listSessions()` is spread raw into four contracts). Precedence `dialog > approval > question > turn-end`, oldest within a kind; approval outranks question because an expired approval resolves *allow* and an expired question denies. `wiring/waiting.ts` is the ONLY `waiting_input` writer; a clear that leaves a reason sends `waiting:true` with the survivor. Inject answers turn-end only and its ambiguity count reads RAW reason lists (a session can hold turn-end + approval). `unmarkWaiting` falls back to `(kind, ref)` when the key is stale after a collapse — never for turn-end, whose ref is `""` everywhere. PWA: one `ANSWERS_TURN` predicate gates header text, auto-follow and the alert, or a background session's dialog would move the composer's target. **`COMPANION_DB_PATH` is not honoured by every sqlite writer** (`learned-allow.ts` builds its own path) — isolated runs can still touch prod. macOS has no `timeout`; `codex exec` needs `< /dev/null` when backgrounded.
- **Phase 10 shipped (2026-09-10, PR #22):** the activity pill lives on `PathState` in `lib/transcript.ts` (`activity`, `lastEventAt`) — the per-session record that already migrates weak→strong identity IN PLACE (a refactor to a spread copy would silently drop the pill). `getActivity()` is the derived rollup ordered on `lastEventAt` (real events only: tool start / prompt / tool end); the heartbeat bumps `lastBeatAt` only, else the rollup would flip every 1.5 s.
